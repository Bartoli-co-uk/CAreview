## Findings

### SEC-001: Loopback bind is not restated at the socket layer beyond the allowlist check, and CAREVIEW_PORT is the only externally influenced startup parameter
- Fingerprint: `careview-server-bind-host-fixed-1`
- Category: configuration/unsafe-defaults
- Severity: Low
- Confidence: Medium
- Blocking: No
- Affected location: `server.py:329-333` (`main()`), `server.py:312-326` (`build_server()`)
- Evidence: `main()` calls `build_server(HOST, port)` where `HOST = "127.0.0.1"` is a module constant not influenced by environment or arguments; only `port` is taken from `CAREVIEW_PORT`. `build_server()` does validate `host` against `_LOOPBACK_BIND_ADDRESSES` and raises `ValueError` otherwise, so the defence-in-depth is real, but as currently wired through `main()` there is no live code path that could pass a non-loopback host in normal operation — this is a strength, not a weakness, but it also means the guard is currently untested against `main()`'s actual invocation (it's only exercised by whatever calls `build_server()` directly, e.g. tests).
- Attack preconditions: none under current code; this is a note about defence depth and testability, not an exploitable path today.
- Impact: none currently; if a future change threads a host argument from environment/CLI into `main()` without preserving the `build_server()` guard call, the bind could silently become non-loopback.
- Exploitability: not exploitable in the reviewed commit.
- Recommended remediation: consider a unit test that calls `build_server()` (or `main()`-equivalent logic) with a non-loopback host string to prove the `ValueError` guard fires, and/or a comment at the `HOST` constant noting it must never become environment-controlled without re-adding that check on the new path.
- Verification method: code inspection; `grep -n "CAREVIEW_PORT\|HOST ="  server.py` confirms only port is env-controlled.
- Disposition: informational, non-blocking; no code change required for M1 acceptance.

## Conclusion and limitations

Based on the evidence gathered — reading the full source of `server.py`, `auth.py`, `graph.py`, `analyzer.py`, `web/app.js`, the CSP-relevant portion of `web/index.html`, targeted greps for dangerous patterns, the CI workflow file, and independently executing `python3 -m py_compile $(git ls-files '*.py')` (clean) and `python3 -m unittest discover -s tests` (83 tests, all passing) against the exact candidate SHA `6311a11a48a0a7e51e83a14ca4081d431cb46698` — I found no critical or high-severity security defects. The code demonstrates deliberate, consistent security engineering matching the documented threat model and the roadmap's stated defences: a Host-header loopback allowlist (DNS-rebinding defence), an Origin check on state-changing POSTs (CSRF defence), a fixed static-file allowlist plus path-resolution containment (traversal defence), a tenant-string regex allowlist before URL construction (SSRF/redirect defence in `auth.py`), a Graph-host validation function plus disabled HTTP redirects before every bearer-token-bearing request (token-exfiltration defence in `graph.py`), textContent/DOM-API-only rendering of all tenant- and finding-derived strings in `app.js` (stored/reflected XSS defence — no `innerHTML`, `eval`, or `document.write` found anywhere in that file), a real HTTP `Content-Security-Policy` header plus an HTML `<meta>` CSP, `X-Content-Type-Options: nosniff`, `Cache-Control: no-store` on sensitive endpoints, in-memory-only token storage with no persistence and explicit clearing on logout/expiry/supersession, no logging of tokens or policy content, and a single GitHub Actions workflow with a SHA-pinned `actions/checkout` and `persist-credentials: false`.

One low-severity, non-blocking informational note (SEC-001) is recorded above concerning bind-configuration testability/future-proofing rather than a current exploitable defect.

Limitations of this review: I did not perform or observe a live device-code sign-in or live Graph fetch (correctly out of scope, per the roadmap, as a separately human-approved protected action); I did not exhaustively line-review every individual rule body in `rules.py` beyond its header/helper functions and the generic requirement-enforcement wrapper in `analyzer.py`; I did not execute `scripts/validate_repo.py` or the PowerShell review launcher; and I have no visibility into provider-side (Microsoft, GitHub Actions runner, or model-provider) retention or isolation guarantees — those remain unverifiable from this vantage point, consistent with `docs/security-boundaries.md`. This report is supplementary evidence for the human's milestone decision; it does not certify the project as secure, compliant, or free of vulnerabilities, and it is not a substitute for qualified independent security testing or the still-outstanding live-tenant evidence gap the roadmap documents.
